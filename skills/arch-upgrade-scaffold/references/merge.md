# The merge table

Step 6 resolves each conflict of the merge by this table, and reads
against it each path a clean merge added or changed. A path that
starts with `../` is read from the skill's folder as `realpath`
resolves it.

| Where | Resolution |
|-------|------------|
| A line both sides changed | The scaffold's change to the core, and the copy's product around it. When both changed it to the same effect in other words, keep the copy's line: its own tests may hold its wording. When the scaffold's change undoes a deviation the copy records (its Deviations table names the ADR), keep the copy's line. |
| A list that holds the marker line (`A copy adds its entries below this line.`) | The scaffold's entries above the marker, as the scaffold has them, and every entry of the copy's below it, in the copy's order. A copy's entry that sits above the marker, from before the list had one, moves below it, so the next move meets no conflict there. In a Markdown table, such as the spec's Deviations, the copy's rows are the ones the scaffold's table lacks, and they move into a table of the copy's own below the marker, under the same header (`../_shared/scaffold-conventions.md`, Changing existing files). An entry reaches only what the function that holds its list takes. One that needs a manager the root builds after that function, such as a waiter whose manager the copy builds below the root's marker, takes the graph bound at call time, as the outbox takes the work manager in `build_managers`: the function gains a last keyword-only parameter, `managers: Callable[[], Managers]`, and the root's call passes `managers=lambda: managers`. Those two are the copy's lines in the scaffold's signature and call, which the next move merges as a line both sides changed. |
| A file the copy deleted and the scaffold changed | It stays deleted (`git rm`), unless it is an ADR, which the `docs/adr/` row decides. When the copy keeps its own file for the same thing, such as a screen its product replaced, carry into that file what the scaffold's change alters in behaviour. |
| A file the scaffold deleted and the copy changed | Deleted, unless the copy's own code still imports or runs it. What the copy added to the file moves first to where the render moved the file's own content, as the copy's entry there: an operator route the copy added to a router the render removed goes to the router of its namespace, beside the render's. The file then goes. |
| `docs/adr/` | An ADR the scaffold gave is the scaffold's, and the copy never edits it (Records of Decisions): it takes the scaffold's change, and its removal, as any file does. The copy's edits to them are `git diff --diff-filter=M $(git merge-base HEAD scaffold) HEAD -- <root>/docs/adr`, read before the merge commits. An ADR the copy edited takes the scaffold's text, on a conflict and on a clean merge alike (`git checkout scaffold -- <file>`), and what the copy's edit added moves into an ADR of the copy's own, numbered from 1001, which cites the scaffold's by number and title (`ADR 0002, Technology choices as adopted`); a citation in the copy of the scaffold's number for that part names the copy's ADR. An ADR the copy deleted and wrote again under the scaffold's number, in a file of another name, is one the copy edited: the render's file comes back (`git checkout scaffold -- <file>`), the copy's file goes (`git rm`), and what it adds to the scaffold's decision moves into an ADR of the copy's own the same way. An ADR the scaffold removed, which the copy edited, goes (`git rm`) once the copy's own ADR states what of its decision the copy still holds, citing no removed number. A copy numbers its own ADRs from 1001 and meets no clash; a copy numbered before may. A new scaffold ADR whose number the copy already uses takes one above the copy's highest number at 1001 or above (1001 when it has none; a number is never reused), when its decision holds in the copy, and is removed when it does not. Each line the merge brings that cites its old number (a link, an `ADR-NNNN`, an `adr =` path; `git diff HEAD` shows them) names its new number, or drops the citation when the ADR was removed: `arch-check` cannot tell, since the old number still names a file, the copy's own. The copy's own citations of that number stay. On a later move, a scaffold change to that ADR goes into the file under its new number, and the citations of the old number that move brings are rewritten the same way. After the merge, no two ADRs share a number. |
| A migration | The chain the copy's databases applied: an applied file is never edited, and a chain the copy folded stays as the copy folded it. A scaffold migration that is not in the copy's chain stays out, a fold of the scaffold's own chain included. When it changes a table the copy has, the copy writes its own migration for that change, on its chain's head. When the render folded a chain, the fold holds no step to follow: the copy writes its migration from the revisions written for the change, as the history of the repository that wrote them holds them before the fold. This guideline's history holds the scaffold's chain, and a layer's history holds its own chain alone: a layer takes each release of its source as one render, already folded. Each history is read between two commits, `<from>` and `<to>`, from the source down. In the source, they are the `Scaffold-Commit` of the base and of the target's render (`git log -1 --format=%B scaffold --`). Beneath a layer, they are the `Scaffold-Commit` of the last render the layer holds at each of its own two (`git log -1 --no-merges -E --grep='^Scaffold-Commit: [0-9a-f]{40}$' --format=%B <commit>`). The `Scaffold-Source` beside them names the repository. In each, `git fetch <repository> <to>`; the fold is `git log -1 --format=%H --diff-filter=D --invert-grep -E --grep='^Scaffold-Commit: [0-9a-f]{40}$' FETCH_HEAD -- scaffold/acme_root/om/migrations/sql`, which passes over the renders a layer took. When it prints nothing, or a fold `<from>` already holds (`git merge-base --is-ancestor <fold> <from>` exits 0), the move folded nothing there. Otherwise `git diff --name-only --diff-filter=A <from> <fold>^ -- scaffold/acme_root/om/migrations/sql` lists the revisions, each read with `git show <fold>^:<path>`. They carry the scaffold's names (`acme`, and `acme_system` in grants and policies); the copy's migration writes them in the copy's names, as its render does. A migration that renames a table or a column renames its not-null constraints with it, to `<table>_<column>_not_null`, the names a fold's tables take. A layer applies no database: the scaffold's migrations come in as the scaffold has them, on the first take and on every move, a fold included. The layer's own migrations follow them: the first of each role's own chain has the scaffold's head as its `down_revision`, re-pointed to the new head when a move brings one, so each role keeps one head. Only that parent moves: no migration is renamed or re-stamped, the scaffold's or the layer's own, released or not. A chain is ordered by its parents, never by its stamps, so an own migration whose stamp sorts below the new head's keeps its name, and a tree built on the layer meets no renamed file on its next move. |
| `scripts/release_before_deselect.txt` | The render's header, then the lines the copy's release before needs on the merged schema, each under the render's comment that says why: of the render's ids, those whose test the copy's main branch holds, and each test of the copy's own that reads a table or a column the move renames, which the release-before job names when it fails on it. |
| `uv.lock`, `pnpm-lock.yaml` | Never merged by hand: take the copy's (`git checkout --ours <file>`), and regenerate after the manifests merge (`uv lock`, `pnpm install --lockfile-only`). A lockfile the merge left without a conflict stays as merged while its check passes (`uv lock --check`, `pnpm install --frozen-lockfile`); when a check fails, that lockfile regenerates from the merged one with the same commands, never from the copy's. |
| What `make openapi` writes under `<root>`: `clients/openapi/`, `clients/typescript/src/schema/`, and `clients/python/src/<package>/client/schema/`, where `<package>` is the `package` under `[tool.arch-check]` in `<root>/pyproject.toml`: the copy's name in a copy, `acme` in a layer | Take either side, then run `make openapi` in `<root>`, which writes each folder afresh. A generated file it no longer writes goes (`git rm`). |
| The pin | Every pin names this guideline's release, never a layer's ref. In a copy of this guideline, every pin names the target: `specs/architecture.md` and the Makefile's `ARCH_CHECK`. `grep -rn "v<base release>"` finds nothing outside the ADRs and a changelog. In a copy of a layer, and in a layer, a pin takes the source's line: the release of this guideline the source took. |
